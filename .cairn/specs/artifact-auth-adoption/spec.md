# Artifact Auth Adoption Specification

## Purpose

Defines the `artifact-auth-adoption` capability.

## Requirements

### Requirement: Valence adopts one immutable reviewed source

r[valence.artifact_auth_adoption.source] Valence MUST consume `artifact-auth-core` and `artifact-auth-ed25519` from one immutable reviewed `OnixResearch/onix-artifact` revision with aligned Cargo and Nix identities, exact complete source-workspace and release-profile membership, compatible licensing, and a consumer graph limited to those two authentication packages.

#### Scenario: Current source cohort is admissible

- GIVEN Cargo and Nix resolve the same reviewed immutable revision, its complete source workspace and release profile agree, and authentication entry-point bytes match reviewed identities
- WHEN Valence evaluates dependency admission
- THEN it SHALL admit only the two authentication packages and SHALL reject floating, duplicate, mismatched, sibling-path, graph-widening, byte-drifted, or license-incompatible selections.

### Requirement: Valence retains protocol, identity, and authorization authority

r[valence.artifact_auth_adoption.authority] Valence MUST retain Radicle protocol verification, actor authorization, Evidence IR identity/roles, COB reduction, Git measurement/storage, SSH-agent effects, lifecycle handoff, and release interpretation while treating standalone authentication as one bounded post-verification input.

#### Scenario: Authentication passes without actor or evidence authority

- GIVEN a standalone mapped decision passes over an already protocol-verified observation
- WHEN actor authorization, Evidence IR, lifecycle, or release interpretation runs
- THEN Valence MUST still require its product-owned checks and MUST NOT promote standalone success into product authority.

### Requirement: Cutover requires explained dual-run evidence

r[valence.artifact_auth_adoption.cutover] Valence MUST dual-run legacy and standalone projections over identical verified observations, classify every preimage, identity, decision, issue, and non-claim difference, reject unrelated-failure false parity, and preserve a bounded legacy rollback until standalone authority is explicitly admitted.

#### Scenario: Unexplained or lossy mapping blocks cutover

- GIVEN any unexplained, lossy, authority-widening, or source-identity difference
- WHEN Valence evaluates cutover admission
- THEN the legacy path SHALL remain authoritative and the exact blocker SHALL be recorded without weakening protocol, identity, authorization, lifecycle, or release gates.

### Requirement: Unified Artifact workspace source transport

r[valence.artifact_auth_adoption.radicle_transport] Valence MUST consume the two authentication packages from the exact reviewed unified Artifact revision recorded by its current Cargo/Nix pins and source-admission constants while retaining predecessor source identities and receipts as historical evidence only.

#### Scenario: Inconsistent owner profile blocks admission

- GIVEN the immutable owner manifest and release profile declare different source package sets
- WHEN source admission runs
- THEN it MUST reject the cohort without narrowing validation to consumed sub-crates or importing transfer or binding authority.

### Requirement: Cargo and Nix lock agreement

r[valence.artifact_auth_adoption.lock_agreement] Cargo manifests, `Cargo.lock`, `flake.nix`, and `flake.lock` MUST identify the same unified Artifact repository and reviewed Git revision while preserving the exact Nix content identity and two-package Valence consumer graph.

#### Scenario: Locks are regenerated by their owning tools

- GIVEN a coherent reviewed owner source and regenerated Cargo and Nix locks
- WHEN full-source admission and its positive/negative checks run
- THEN exact repository, revision, package graph, NAR, source-byte, and license identities MUST agree and mismatches MUST fail closed.

### Requirement: Behavioral parity checks r[valence.artifact_auth_adoption.behavior]

The source migration MUST preserve existing Valence and artifact-auth behavior under focused positive and negative mapping, shell, workspace, no-std, formatting, and Clippy checks without Rust implementation changes.

#### Scenario: Existing positive and negative behavior passes

- GIVEN the unified source at the reviewed commit
- WHEN the focused and workspace suites run
- THEN existing acceptance and rejection behavior MUST pass without Rust implementation changes.

#### Scenario: Behavioral drift blocks acceptance

- GIVEN any changed fixture result, feature graph, package version, source entry point, or authority boundary
- WHEN parity is evaluated
- THEN the migration MUST not be accepted.

### Requirement: No mixed or automatic source fallback r[valence.artifact_auth_adoption.fallback]

Valence MUST use only the admitted unified source in executable manifests and locks and MUST NOT automatically select the predecessor repository, a sibling path, or a floating source.

#### Scenario: Unified source is unavailable

- GIVEN the admitted source cannot serve the exact object
- WHEN dependency resolution runs
- THEN resolution MUST fail visibly rather than selecting another source.

#### Scenario: Historical evidence remains bounded

- GIVEN documentation and archived receipts name the predecessor GitHub and Radicle sources
- WHEN active-source validation runs
- THEN historical evidence MAY remain while executable manifests and locks contain only the admitted unified source.

### Requirement: Typed source migration evidence r[valence.artifact_auth_adoption.radicle_evidence]

Valence MUST emit typed Nickel/JSON evidence with a BLAKE3 sidecar that binds the unified source, source and consumer package sets, source-byte parity, test observations, rollback boundary, and non-claims while retaining the prior Radicle receipt as historical evidence.

#### Scenario: Complete migration evidence passes

- GIVEN matching source, package, parity, lock, and test observations
- WHEN receipt validation runs
- THEN it MUST accept deterministically.

#### Scenario: Missing linkage or overclaim fails

- GIVEN source drift, package widening, missing negative evidence, automatic rollback, absolute evidence paths, or weakened non-claims
- WHEN receipt validation runs
- THEN it MUST fail closed.
