# Source Review Acceptance Specification

## Purpose

Defines the `source-review-acceptance` capability.

## Requirements

### Requirement: Independent authenticated manual-review acceptance

r[valence.source_review.independent_acceptance] Valence MUST independently verify Cairn source-review attachment signatures against explicit operator policy, binding exact source subject, claim root, reviewed policy, verifier context, full public-key identities, exclusive review purpose, generation, currentness, author exclusion, and distinct-key threshold without consuming a Cairn verdict.

#### Scenario: Authorized test-only approval

- GIVEN an externally signed approved attachment and matching current authorized test-only verification policy
- WHEN the actual Valence source-review CLI verifies the exact input bytes
- THEN it SHALL emit an accepted manual-review receipt whose non-claims remain intact and SHALL NOT grant release authority or represent actual human approval.

#### Scenario: Tampered or unauthorized review

- GIVEN substituted source bytes, revoked currentness, or an excluded author key
- WHEN the same receiver verification path runs
- THEN it MUST reject approval and emit an invalid or insufficient manual-review receipt.

### Requirement: Negative dispositions never count as approval

r[valence.source_review.negative_disposition] Valence MUST authenticate `needs_revision` only as attribution and MUST NOT count it toward an approval threshold.

#### Scenario: Authenticated request for revision

- GIVEN an externally signed `needs_revision` attachment under matching authorized policy
- WHEN Valence evaluates the approval threshold
- THEN it SHALL emit insufficient acceptance with no approved keys rather than accepted manual review.

### Requirement: Capability-confined bounded receipt publication

r[valence.source_review.cli_boundary] The source-review CLI MUST confine input and output locators to explicit capability roots, enforce input byte bounds, publish the bounded acceptance receipt without overwriting an existing destination, and reject traversal before creating output.

#### Scenario: Existing receipt or escaping locator

- GIVEN an existing receipt destination or an absolute or parent-traversing locator
- WHEN the CLI reads evidence or publishes the receipt
- THEN it MUST fail without overwriting existing bytes or creating escaped output.

### Requirement: Current owner-policy compatibility preserves trust

r[valence.source_review.policy_compatibility] Valence MUST regenerate its repository-owned policy from scoped Nickel inputs through the supported Cairn exporter and admit the generated bytes through the supported parser while retaining positive/negative fixture enforcement and existing trust, function-address, traceability-root, and archive-destination settings.

#### Scenario: Compatible owner workflow schema

- GIVEN current workflow schema declarations, strict typed task markers, declared traceability assurance, and exact marker anchors
- WHEN export freshness, fixtures, parser admission, native root status/list, and lifecycle gates run
- THEN all checks MUST retain their original validation boundary without selecting or merging lifecycle roots implicitly.

### Requirement: Bounded current receiver evidence

r[valence.source_review.cohort_evidence] Valence MUST record current immutable owner pins, source content identities, exact verification commands, working directories, observed exits, native gate verdicts, and test-only receiver receipts separately from unchanged historical typed migration receipts. Current receipt subjects and test-only limitations MUST remain explicit and MUST NOT be relabeled as real manual review, publication, or release authority.

#### Scenario: Fixture approval remains bounded

- GIVEN current receiver proof over the retained external-signer test-only fixture subject
- WHEN the command records and acceptance receipts are retained with BLAKE3 identities
- THEN they MUST remain distinguishable from review of the actual Valence source and MUST NOT rewrite prior source-migration acceptance or authorize an automatic fallback.
